Scrapling 融入 NiKo 赛事站：爬虫改版自愈与反爬突破实战

记录时间：2026-10-03　｜　场景：静态赛事跟踪站，数据源为 Liquipedia 赛事页 + HLTV 逐图评分
一句话结果：页面改版后关键区块自动救回（模拟改版 2/2），逐图评分覆盖率从 5/58 提升到 56/58（97%）

一、要解决的两个痛点

痛点一：源站改版导致解析器静默失效。
Liquipedia 赛事页一旦调整 DOM 结构，主解析器就会返回空结果，而旧逻辑把空结果当成正常数据写回线上，页面整块内容直接消失，且没有任何报错提示。

痛点二：HLTV 逐图评分抓不到。
HLTV 的 mapstats 页面全站套了 Cloudflare 挑战，普通请求库、常规无头浏览器、公共代理全线被拦，58 场比赛只拿到 5 场评分。

二、方案总览

维度方案 A：Selector 改版自愈方案 B：StealthyFetcher 反爬突破
要解决的问题源站改版后元素定位失效Cloudflare 人机验证拦道

两者的内核思路一句话讲清楚：

  • 方案 A（自愈）：完全不动主解析器已经成功解析的字段，只在「某一块为空」时用 Scrapling 的 Selector 按强判据补一次，作为兜底的最外一层。
  • 方案 B（反爬）：用 Scrapling 的 StealthyFetcher 起真实浏览器并自动解 Cloudflare 挑战，突破后做增量回补，结果落进持久库。

三、方案 A：Selector 改版自愈（核心是「绝不覆盖 + 强判据」）

3.1 接入位置

新增独立文件 parse_event_sl.py；主解析器 parse_event.py 的 build() 增加可选 url 参数——只有传入 url 时才启用自愈层。这样本地测试与 CI 完全隔离，自愈出问题永远不会污染主链路。

调用形态：

Selector(raw, url=url, adaptive=True,
         storage_args={"storage_file": "_cache/scrapling/adaptive.db"})

两个必须记住的点：

  1. adaptive=True 必须在初始化时显式开启，否则后续 css(..., adaptive=True, auto_save=True) 会被静默忽略，指纹永远不会落盘。
  2. storage_args 必须显式传 storage_file，否则每次进程起来都是全新的空指纹库，等于自愈做了个寂寞。

3.2 触发规则：只补空，不覆盖

主解析结果自愈层行为
有值完全不动，原样返回
为空尝试补一次；补到就采用，补不到就保持空

同时返回 selfhealed 列表（记录哪些字段是靠自愈补回来的）用于 CI 日志打印，一眼就能看出这次是不是靠兜底救的，以及哪一页在劣化。

3.3 强判据清单（全文最重要的一节）

第一版图省事，用宽选择器 a[href^="/counterstrike/"] 去猜对阵，结果给一个根本没有对阵区块的页面补了 103 条垃圾数据——地图名、选手名、分类名（形如 Category:New Zealand）全被当成队伍名写进了线上。

教训写在第一行：宁可不补，也绝不能补脏数据。 补错数据比不补更糟，因为它不会报错，只会静静地污染页面。最终定下的门槛：

字段定位锚点必须满足的判据
brackets（分支图）自定义数据属性为首选锚点，缺失时退到无障碍标签双方队名不可相同；至少一方要有比分或时间戳；队名须通过黑名单校验
upcoming（即将开始）带时间戳的计时元素 + 队伍区块必须同时有双队和时间戳，缺一不认
groups（分组积分）同一个表格容器内行数达到 4 行才认可，不足就宁可不补
participants（参赛名单）不独立猜测只从已通过校验的分组与赛程反推，且优先级低于主页面名单

补充的队名过滤规则（ok_team()）：排除含 Category:、含斜杠 /、纯数字、以及命中地图名黑名单的字符串。

3.4 两个细节坑

  • 向上找祖先不能贪大。 一开始从锚点一路向上遍历到最外层容器，一个容器里囊括 28 个比赛项，结果只抽出 1 场。改成找最小公共祖先，时间戳先在容器子树里找、找不到再往上退一层。
  • 不是所有赛事页都有对阵数据。 有些赛事页本身就没有 brackets 区块（例如某站 S24 赛季），自愈必须诚实地返回 0，不能硬凑。做法是「主锚点失败可 fallback 到次选锚点，但通过门槛一律不降」。

3.5 参赛名单的权威优先级

自愈曾经把某赛事的参赛队从 24 支缩到 8 支——因为自愈只反推了当前可见的分组与赛程里出现的队伍。修正后规则：主页面的完整名单（teams_page）优先级最高，自愈结果只在主页面也给不出名单时才兜底使用。

四、方案 B：StealthyFetcher 突破 Cloudflare

4.1 正确调用姿势

StealthyFetcher.fetch(url, headless=True, solve_cloudflare=True, timeout=60000)

三个踩过才知道的参数坑：

  1. solve_cloudflare=True 必须显式传。 不传就等于没带 stealth 武器，直接吃 403。第一次上线就是漏了这个参数，白跑一轮。
  2. 绝对不要加 disable_resources=True。 它会连 Cloudflare 的验证 JS 一起屏蔽，反而让挑战必然失败——这是最反直觉的一条。
  3. 返回对象用 .html_content，它没有 .status 属性。 别按常规 HTTP 库的习惯去读状态码。

策略上：连续 2 次 Cloudflare 挑战失败就停，避免长时间空转；失败后自动回落到普通请求。

4.2 住宅 IP 与数据中心 IP 的天壤之别

本机住宅 IP 实测稳定突破，约 16 秒一张图；而 CI 的数据中心 IP 段不保证能过，不要指望 Actions 全自动回补这条路。结论：本机回补 + 持久库入库才是主路径，CI 只作为锦上添花。

4.3 幂等入库

给回补脚本新增 --merge 参数，把持久库里的评分条目幂等地写进主数据文件的对应字段，之后再跑构建。同时支持 --max N 控制单次回补量，方便分轮跑避免长时间占用带宽。

五、CI 集成要点

  • requirements.txt 只放轻量依赖，CI 不装完整的浏览器抓取扩展包（那是几百 MB 的依赖）。缺少 Scrapling 时自愈层自动禁用，主流程照常运行。
  • 指纹库 _cache/scrapling/adaptive.db（约 4KB）用 actions/cache 持久化，且只在数据健康时才写回。否则一次失败的运行会把错误指纹写进库里，毒化后续所有运行——这是自愈类方案最容易忽视的隐蔽风险。
  • 该缓存目录已加入忽略列表，不进版本库。

关键佐证：20 页全量回归零劣化（字段只增不减，其中 17 页有实际补齐）；改版模拟（把页面的 class 名整体改掉）后 brackets 从 1 掉到 0、schedule 从 7 掉到 0，开启自愈后 2/2 全部救回，且救回的内容是真实对阵（含决赛的比分与时间戳），不是凑数数据。

七、可复用清单

下次给别的站点接自愈层，按这个顺序走：

  1. 先把铁律定死：主链路绝对不能被自愈污染，只补空、不覆盖，自愈层永远是最外一层兜底。
  2. 自愈的选择器一律用语义化锚点（自定义数据属性、aria-label 这类），绝不依赖层级路径和 class 名。
  3. 每条候选结果都要同时具备正例判据（必须有比分或时间戳这类强信号）和黑名单过滤（地图名、选手名、分类名、纯数字）。
  4. 上线前必跑两件事：全量回归比对（字段只增不减）＋ 改版模拟（改 class 看能否救回）。
  5. 抓不到时在页面上明示「已收录 N/M」，不要用可能错的数据填满——空态比错态安全得多。
  6. 涉及第三方反爬的数据回补，不要把希望寄托在 CI 上，住宅 IP 的本机运行才是稳定路径。
